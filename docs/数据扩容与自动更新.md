## 调度行为

交易日北京时间 `09:30`、`11:30`、`13:00`、`15:00` 各触发一次。
常驻进程每60秒检查，通常在时点到达后的60秒内开始；触发后采集还需要数分钟，并非瞬时全量更新。
业务时间固定为 UTC+8（Asia/Shanghai），不跟随服务器的欧洲时区或夏令时。

- 周末跳过；工作日通过扶摇同日交易日历确认，节假日返回空列表则跳过。
- 日历请求失败时不猜测开市、不采集；持久化失败记录，等待10分钟后重试。
- 完成记录持久化；进程重启只补当天最近一个到期时点，不重放全部历史任务。
- 单次数据请求最多4次尝试、指数退避；全局串行限速，估值每批100只、K线每批10只、财报逐只查询。
- 整批失败从失败结束时算起至少等待10分钟后再尝试同一时点；操作系统文件锁防止多个进程同时发布。
- 自动任务须独立于 FastAPI 运行，避免开发 reload 或 API 多进程造成重复采集。

## 清洗与质量规则

1. 标准化并去重股票代码，校验完整代码格式；少于目标数量则拒绝发布。
2. 空值、非数字、NaN、Infinity 保持 `null`。负 PE 保留，筛选引擎仍将其排除在正PE估值条件之外。
3. 日K线按上海交易日期排序、去重，冲突记录剔除；收盘价必须为正且有限。
4. 盘中排除当日未收盘日K，要求最近21个完整交易日齐全才计算20日收益率样本标准差；缺日/停牌等留空，不用跨日缺口冒充单日收益。
5. 15:00后尝试纳入当日数据。若上游还未更新，质量门槛可能拒绝本次快照，worker随后重试，保留上一份数据。
6. 财务指标从最近已结束季度向前尝试最多4期，并保留实际报告期；不把季度结束当作财报已披露，不把普通净利润字段替代归母净利润字段。
7. 三个核心字段默认各至少80%有效覆盖。这个比例是工程发布门槛，不是金融判断；部分缺失仍会以 `UNKNOWN` 进入筛选。
8. 校验通过后先留存历史，再原子替换当前快照；失败不覆盖旧快照，不把旧值冒充本次新数据。

日历、接口请求 ID、逐股数据时间和清洗异常保留。采集成功不保证上游数据每次都变化，财报尤其不会每天生成四份新内容。

## 文件与配置

```text
backend/collect_data.py          # 单次采集、清洗、校验、发布
backend/refresh_worker.py        # 四时点调度，可独立运行
backend/requirements.txt         # 当前已验证的后端依赖
deploy/stocklens-refresh.service # Linux systemd 常驻服务模板
deploy/refresh.env.example       # 服务器环境文件示例，无真实凭据
data/stock_snapshot_latest.json  # 默认读取的当前快照
data/history/<snapshot_id>.json  # 通过校验的历史快照
data/refresh_status.json         # 最近采集进度/成功/失败
data/scheduler_status.json       # worker 最近检查状态
data/calendar_today.json         # 当天交易日历确认结果
```

`STOCKLENS_DATA_DIR` 默认为项目 `data/`；API 和 worker 必须使用相同目录。
`STOCKLENS_UNIVERSE_LIMIT` 默认300；`STOCKLENS_MIN_COVERAGE` 默认0.8。
`STOCKLENS_REPORT` 通常不设；若设为 `yyyy-1` 至 `yyyy-4` 则固定查询该报告期，不自动向前尝试。
`STOCKLENS_SNAPSHOT` 显式指定文件的优先级最高；启用自动更新时应去掉旧5只快照的固定配置。
采集脚本会加载根目录 `.env`，已有进程环境优先；不输出凭据。

历史快照当前不自动删除。一次300只快照约0.9MB，服务器需要配置持久存储和独立的保留/备份策略；原型文件锁适用于共享本地磁盘上的单服务器，不用于多节点集群。


## Linux 服务器部署模板

以支持 systemd 的 Linux 服务器、Python 3.10+ 为例，部署目录 `/opt/stocklens`，数据目录 `/var/lib/stocklens`。
以下是待在目标服务器执行的步骤，并未在本机执行：

1. 将源代码放到 `/opt/stocklens`，创建运行账户 `stocklens`，确保代码可读。
2. 创建虚拟环境并安装依赖：

```sh
python3 -m venv /opt/stocklens/.venv
/opt/stocklens/.venv/bin/pip install -r /opt/stocklens/backend/requirements.txt
```

3. 创建 `/etc/stocklens/refresh.env`，参考 `deploy/refresh.env.example`，在服务器填入扶摇凭据，设置文件权限600、所有者 `stocklens`。不要把文件加入仓库。
4. 复制服务模板到 `/etc/systemd/system/stocklens-refresh.service`，确认 `User`、目录和解释器路径。模板使用 `StateDirectory=stocklens` 创建可写持久数据目录。
5. 为 API 配置相同的 `STOCKLENS_DATA_DIR=/var/lib/stocklens`。API 启动无需启动第二个 worker。
6. 加载并启动 worker：

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now stocklens-refresh.service
sudo systemctl status stocklens-refresh.service
sudo journalctl -u stocklens-refresh.service -n 100
```

首次部署可先运行一次手动采集，或者将当前经过校验的快照放入持久目录；仅启动时点调度可能要等到下一个交易时段才有首份数据。
FastAPI、前端同域代理、HTTPS 与密钥配置模板已补齐，见 [服务器部署](服务器部署.md)；尚未在目标服务器安装运行。

## 验收与运行监测

- `GET /api/data/status` 应返回300只、快照ID、采集时间、覆盖率，以及 `refresh` / `scheduler` 状态。
- 前端每60秒更新状态；筛选结果显示其自己的快照时间。调整条件默认沿用原快照；选择“使用最新数据重新筛选”才主动换数据并重新建立比较起点。
- `/api/screen` 与 `/api/compare` 可传入本次筛选的32位十六进制 `snapshot_id`，从历史目录读取同一份数据。原快照不可用返回409，格式非法返回422，不会静默换成最新数据。
- 规则对比是在原快照上重算前后条件，不表示股票价格或行情变化。
- 本地回归测试涵盖限流、清洗、季度切换、财报回退、发布失败保护、并发锁、节假日、时区、重启补偿及快照竞争。
- 真实300只采集通过；持续四时点运行、服务器重启恢复与服务安装仍须在目标服务器验收。
