# 服务器部署

当前推荐方案为[Docker生产部署](../DEPLOYMENT.md)。下文保留为已有systemd方式的备选说明；同一份数据目录只能启用一种调度部署，切换Docker时停用旧worker，避免重复采集。

状态：提供单台Linux + systemd + Caddy模板，尚未在真实服务器启用。生产验收需要实际域名、HTTPS和持续运行记录。

## 结构与配置

浏览器 → Caddy静态前端与同源 /api → FastAPI 127.0.0.1:8000。独立worker采集金融快照；API与worker共用 /var/lib/stocklens。账号SQLite也放在持久目录。

1. 源码放 /opt/stocklens，使用Python 3.10+、Node 26创建环境并安装锁定依赖；在frontend执行npm ci和npm run build。
2. 创建stocklens服务用户。按deploy/api.env.example和refresh.env.example创建/etc/stocklens/api.env、refresh.env，所有者stocklens、权限600。
3. API设置STOCKLENS_ENV=production，账号库指向/var/lib/stocklens/accounts.sqlite3，两服务数据目录一致。生产不使用本地.env。不要复制Windows虚拟环境、node_modules或真实密钥入库。
4. 按相同服务环境执行首次完整采集；成功后才有可用快照。管理员生成邀请码时必须使用API同一账号库路径，不公开邀请码。
5. 修改deploy/Caddyfile.example中的域名，配置DNS和80/443。静态目录只指向frontend/dist，不暴露data或项目根目录。

## 服务

模板为deploy/stocklens-api.service和stocklens-refresh.service。两者使用StateDirectory=stocklens保证持久目录可写，与ProtectSystem=strict兼容。

    sudo cp deploy/stocklens-api.service deploy/stocklens-refresh.service /etc/systemd/system/
    sudo systemd-analyze verify /etc/systemd/system/stocklens-api.service /etc/systemd/system/stocklens-refresh.service
    sudo systemctl daemon-reload
    sudo systemctl enable --now stocklens-api stocklens-refresh
    sudo caddy validate --config /etc/caddy/Caddyfile
    sudo systemctl reload caddy

请合并已有站点配置，不覆盖其他站点。采用同源HTTPS时CORS来源可留空；分域时必须显式配置来源，并在构建前设置VITE_API_BASE_URL。生产会话使用Secure Cookie。

## 上线验收与运营边界

- 检查/api/health、服务状态与日志；未登录的受保护API应返回401。
- 用受邀账号走通解析、筛选、策略保存和恢复，确认不同账号不能读取彼此策略。
- 观察交易日GMT+8的四时点调度，失败保留旧快照、重启不重复成功时点；不能用模拟时间测试代替真实持续运行验收。
- 备份账号库和金融快照。历史快照暂无自动清理；删除后相关旧比较可能返回409。
- 每账号与全站每日调用上限用于控制用量；失败/超时也占额度，不是精确账单。设置适合内测规模的上限。
- 转发真实客户端地址必须由可信代理处理。API只监听回环地址，数据库不暴露公网。
- 当前没有自助找回密码、网页管理员后台及自动告警。先安排人工恢复、备份和额度管理流程，再邀请正式用户。

本指南是部署步骤，不是已完成部署或安全审计的声明。
